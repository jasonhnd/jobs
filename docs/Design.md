## §2.5 色調（アルファ）の表し方 `[確定]`

> **オーナー裁定 2026-09-17。** v1.1 で追加。

**罫・淡色面・グラデーションの色調は、既存トークンから `color-mix()` で作る。**
生の `rgba()` を書かない。

```css
/* 不可 */  border: 1px solid rgba(217, 107, 61, 0.16);
/* 可   */  border: 1px solid color-mix(in srgb, var(--orange) 16%, transparent);
```

### 根拠

実装側には色調が 71 箇所あり、うち **38 箇所の基色は調色板のトークンそのもの**だった
（`rgba(217,107,61,·)` = `--orange`、`rgba(201,90,58,·)` = `--red` など）。alpha は 27 種に
散っており、「色調スケール」を新設して収束させれば**現行の色が変わる**。

`color-mix()` は**トークンを 1 つも増やさずに**同じ色を表現できる。実測でも
`color-mix(in srgb, var(--orange) 16%, transparent)` と `rgba(217,107,61,.16)` は
8 組すべてで**逐位一致**した（srgb 補間のため）。

対応: `color-mix()` は Baseline 2023（Chrome 111 / Safari 16.2 / Firefox 113）。

### 適用範囲

- **調色板のトークンから作れる色調は必ず `color-mix()`。** `check-color-tokens` が失敗させる。
- ブランド色（例: LINE の `#06C755`）や調色板に無い基色は対象外。報告のみ。
- 中性の黒・白の影（`rgba(0,0,0,·)`）は §8.3 の影トークンの領域であり、本条の対象外。

| 区分 | 条件 | 必要比 |
|---|---|---|
| 大きい文字 | **24px 以上**、または **18.66px 以上かつ字重 700** | 3.0:1 |

| high | `#F6E0CC` | `#A24A28` | **4.64** ✅ | 据置 |

**この 3 組が影響度ピルの唯一の配色である。** `color-mix()` や `rgba()` で自前の
淡色面を作らない。#552 の時点で `.band-low/mid/high` `.tc-risk` `.status-stale` の
4 種が独自の淡色を持っており、いずれも 4.0〜4.47 で契約未達だった。

> **`high` 前景を `--risk-soft-4` の上に置かない。** 4.5:1 を満たすのは
> `--risk-soft-3`（4.64）の上だけで、`--risk-soft-4`（`#F0D6CC`）の上では 4.28 に
> 落ちる。`/aiadoption` の `.status-stale` がこれに該当していた。

**色だけで影響度を伝えない。** 必ず数値かラベルを併記する（§11）。

## §2.4 禁止事項 `[移行中]`

- ページ CSS に生の `#hex` / `rgba()` を書かない。**必ず `var(--*)` を経由する。**
  - **調色板トークンから導ける色調は `color-mix()` で書く（§2.5）。CI で強制済み** —
    `check-color-tokens`。2026-09-17 時点で違反 0。
  - 実測（2026-09-17・`drift:design`）: 影を除く生 hex **65 種 212 箇所**、
    生 rgba **41 種 57 箇所**。討論 6 時点の «hex 91 種 312 箇所» から減った。
    残りは**調色板に基色が無い**もの（LINE の `#06C755` 等のブランド色、
    グラデーションの停止色、中性の影）で、§2.5 の対象外。`drift:design` が報告し続ける。
  - 例外 1: `box-shadow` の影色（§8.3 でトークン化するまで）。実測 **52 箇所**。
    v1.2 で `--sh-sheet` を追加し、上向き 2 箇所を収容した。残り 31 箇所は下向き。
  - 例外 2: **`data:image/svg+xml` の中の色**。data URI の内側では `var()` が
    解決されないため、値を直接書くしかない。**ただし書いた値は調色板トークンの
    値と一致していなければならず、`check-color-tokens` が照合する**（v1.2 で追加）。
    これが無いと、トークン側を変えたときにアイコンだけ静かに取り残される。
- `#fff` と `#FFFFFF` の混在をやめる（実測: 3 桁 **30 箇所** / 6 桁 **182 箇所**）。トークン化で自然に解消する。
- ページ側で `:root{}` を再宣言しない（§18.4・CI で強制済み）。

## §4.3 見出しの階層 `[確定]`

> **討論 3（2026-09-14）で合意。** 選択肢 A「Display / H1 / H2 = セリフ、H3 / H4 = サンセリフ 700」を採用。

**見出しは 4 級 + 特集用の Display、合計 5 段とする。** これより増やさない。

| 級 | 用途 | サイズ | 書体 | 字重 | 行間 | 色 | 1 ページの個数 |
|---|---|---|---|---|---|---|---|
| **Display** | 特集ページの hero のみ | `--t-display` 40/32px | **serif** | 単一 | 1.15 | `--ink` | 0 or 1 |
| **H1** | ページ標題 | `--t-h1` 28px | **serif** | 単一 | 1.25 | `--ink` | **必ず 1** |
| **H2** | 主区画の見出し | `--t-h2` 22px | **serif** | 単一 | 1.35 | `--ink` | 制限なし |
| **H3** | 小区画・カード標題 | `--t-h3` 18px | **sans** | **700** | 1.4 | `--ink` | 制限なし |
| **H4** | カード内小見出し・FAQ 設問 | `--t-body` 16px | **sans** | **700** | 1.5 | `--ink` | 制限なし |

### 22px と 18px の間で書体を切り替える理由

**セリフは字重を持っていないから**（§4.5）。配信されているセリフは 1 ファイルのみで、400/500/600/700 すべてが同一に描画される（実測: 同一字号での描画幅が 4 weight とも 595.97px）。

したがってセリフの見出しは**字号だけ**で階層を作るしかない。

- **22px（H2）までは字号差で足りる。** 本文 16px に対して 1.375 倍あり、かつ明朝とゴシックの字面差も効く。
- **18px（H3）・16px（H4）では字号差が足りない。** H4 に至っては本文と同サイズになる。ここで必要なのは字重だが、**字重を持っているのはサンセリフだけ**（実測: 566 → 571 → 575 → 580px と実際に変化する）。

だから H3 で書体を切り替える。H4（16px sans 700）と本文（16px sans 400）は同サイズだが、字重が実際に効くため階層が成立する。

### 現行との比較

| | 現行 | 合意後 |
|---|---|---|
| Display | 規定なし（`/models` が 66.24px を独自実装） | **40px** serif |
| H1 | 27.2px serif 700 | **28px** serif（実質据置・`!important` 廃止） |
| H2 | 18.4px serif 600 | **22px** serif |
| H3 | **16px serif 600（= 本文と同サイズ）** | **18px sans 700** |
| H4 | 規定なし（serif のみ） | **16px sans 700** |
| 本文 | 16px sans 400 | 16px sans 400（据置） |

現行の最大の欠陥は **H3 が本文と同じ 16px** であること。手掛かりは書体（明朝 vs ゴシック）だけで、しかもセリフ 600 はセリフ 400 と同一に描かれるため「字重で強調している」という意図は一切描画に現れない。`/methodology` の FAQ 設問が本文に埋もれて見えるのはこれが原因。

### 見出しの規律

1. **H1 は 1 ページに必ず 1 つ。** 0 個も 2 個も不可。
   - 実測（15 ページ, 2026-09-14）: `/` のみ **H1 が 2 つ**（「AIの時代でも、あなたらしい働き方を。」と「あなたの仕事は、AIでどう変わる？」）。他 14 ページは適合。`/` の 2 つ目を H2 に降格する。
2. **級を飛ばさない。** H2 の次に H4 を置かない。見た目が欲しいだけなら H3 を使うか、見出しではなくラベル（§4.7）を使う。
3. **見た目のために級を選ばない。** 級は文書構造で決める。大きさが足りなければトークンではなく構造を直す。
4. **H5 / H6 を使わない。** 必要になった時点で構造が深すぎる。
5. **Display は H1 の代わりではない。** Feature class の hero では Display を使い、その中に見出し要素としての H1 を 1 つ持たせる（Display は H1 に適用する表示段であって、別の見出し級ではない）。

### 見出しの余白（垂直リズム）

| 級 | 上 | 下 |
|---|---|---|
| Display / H1 | — | `--s-5` (24px) |
| H2 | `--s-7` (48px) | `--s-4` (16px) |

「見出しの上は広く、下は狭く」。見出しは後続の本文に属することを余白で示す。

## §4.4 書体の使い分け `[移行中]`

> **討論 3（2026-09-14）で確認。** セリフの適用範囲は Display / H1 / H2 の 3 段。

| トークン | スタック | 使う場所 |
|---|---|---|
| `--font-serif` | `"Noto Serif JP", "Hiragino Mincho ProN", "Yu Mincho", serif` | **Display / H1 / H2 のみ** |
| `--font-sans` | `"Plus Jakarta Sans", "Hiragino Sans", -apple-system, …` | **それ以外すべて**（H3 以下・本文・UI・ボタン・表・ラベル） |
| `--font-mono` | `ui-monospace, SFMono-Regular, Menlo, monospace` | 数式・コード・ID・スコアの生値 |

### 規則

1. **セリフは Display / H1 / H2 の 3 箇所だけ。** H3 以下でセリフを使わない。本文でセリフを使わない。
2. セリフを「雰囲気づくり」で本文や小さい文字に使わない。日本語明朝は 16px 以下で急速に判読性を失う。
3. **等幅は必ず `var(--font-mono)` 経由。** 生の `monospace` を書かない。
   - 現状の実害: `/aiadoption` は `monospace` と書いたため **Osaka**（丸く幅広い和文等幅）に落ち、`/methodology` `/data` は `ui-monospace` で **Menlo** に落ちている。同じ「数式」という役割が 2 つの別書体で出ている。
4. 数字を並べて比較させる箇所（表の数値列・スコア・統計）は `font-variant-numeric: tabular-nums` を付ける。桁が揃わないと比較できない。
5. 日本語の字面はどのページでも OS 依存（Hiragino Sans / Yu Gothic UI / Noto Sans JP）。**これは受容する。** 制御するのはサイズ・字重・行間であり、和文の字形ではない。

## §4.5 字重 `[移行中]`

> **討論 3（2026-09-14）で確認。** セリフ単一字重、サンセリフ 400 / 600 / 700 の 3 段。

**事実: セリフの字重は現在すべて同一に描画される。**

配信セリフは `noto-serif-jp-600.woff2`（282KB）1 ファイルのみで、これが `font-weight: 400 / 500 / 600 / 700` の 4 つの `@font-face` すべてに割り当てられている。

実測（同一字号での描画幅、px）:

| | w400 | w500 | w600 | w700 |
|---|---|---|---|---|
| セリフ | 595.97 | 595.97 | 595.97 | **595.97** |
| サンセリフ | 566.47 | 570.84 | 575.20 | 579.58 |

h1 の `font-weight:700` と h2 の `600` は**視覚差ゼロ**である。

### 規定

| 書体 | 使える字重 |
|---|---|
| セリフ | **単一**（CSS で `font-weight` を書き分けない） |
| サンセリフ | **400 / 600 / 700 の 3 段のみ** |
| 等幅 | **400 / 600 の 2 段のみ** |

- サンセリフ 400 = 本文・通常 UI
- サンセリフ 600 = ラベル・表ヘッダ・副次強調
- サンセリフ 700 = H3 / H4 / ボタン・強い強調
- `800` / `900` を使わない（現状 `/models` が使用。廃止）
- `500` を使わない（400 との差が小さく、段を無駄にする）
- **セリフ字重を追加配信しない。** +282KB かつ preload 対象で、LCP コストが見出しの重みに見合わない。

## §4.9 上書きの唯一の方法 `[確定]`

> **討論 1・7（2026-09-14）で合意。** canonical から `!important` を外し、変種は `body[data-page-class]` で canonical 側が分岐する。ページ CSS は見出しのサイズ・書体・字重を書かない。

現在、canonical と各ページの間で**特異度の軍拡競争**が起きている。

```
① ページ側      .hero h1                                  (0,0,1,1)
② canonical     html body h1 { … !important }             (0,0,0,3) + !important  → ① に勝つ
③ /models       html body.models-surface .models-hero h1
                { … !important }                          (0,0,2,2) + !important  → ② に勝つ
④ テスト        assertHeroSizeBeatsCanonical()            ③ を固定する
```

canonical のコメントは ② を「hero / nav / detail の変種を canonical に引き戻すため」と説明しており、意図は正しい。しかし `!important` を使った瞬間、逸脱したいページは**より高い特異度の `!important`** でしか対抗できなくなり、③ が生まれた。

### 規定

1. **canonical から `!important` を外す。ただし最後に行う（§4.9.1）。**
2. 変種は**ページ側ではなく canonical 側で**分岐する。`<body>` の `data-page-class` 属性を唯一のスイッチにする。

```css
/* canonical-css.ts — 分岐もここに置く */
html body h1                     { font-size: var(--t-h1); }      /* (0,0,3) */
body.page-feature h1             { font-size: var(--t-display); } /* (0,1,2) → 勝つ */
```

`body` の class は `BaseLayout` の既存 prop `bodyClass` で与える（`models.astro` が `bodyClass="models-surface"` で既に使っている機構）。**新しい prop を足さない。**

特異度は「class 1 個 (0,1,2)」が「要素 3 個 (0,0,3)」に勝つため、`!important` は不要である。

3. **ページ CSS で見出しのサイズ・書体・字重を書かない。** 例外なし。
4. 新しい標題の見え方が必要になったら、ページに CSS を足すのではなく**本書に段を足すか、page class を足す**。

この構造では特異度が競合しないため、`!important` が不要になり、軍拡競争そのものが消える。

### §4.9.1 `!important` を外す順序 — 最重要 `[確定]`

**canonical の `!important` を外すのは、全 surface の移行が終わった後である。途中で外してはならない。**

現在 `html body h1/h2/h3 { … !important }` は、ページ側の **class 付き見出し規則 66 箇所**を抑え込んでいる。

| surface | class 付き見出し規則 | 主なファイル |
|---|---|---|
| `detail` | 10 | `_id-css.ts`(8), `canonical/detail.ts`(2) |
| `misc` | 7 | `_shindan-css.ts`(5), `me.astro`(2) |
| `hub` | 4 | `templates/Hub.ts`(3), `answers/index.astro`(1) |
| `sector` | 3 | `sectors/_sector-css.ts`(3) |
| `doc` | 2 | `canonical/doc.ts`(1), `data.astro`(1) |
| `interactive` | 1 | `_map-css.ts`(1) |

これらの特異度は (0,1,1)、canonical は (0,0,3) + `!important`。**`!important` を外した瞬間、未移行の surface を含むすべてのページ側規則が一斉に復活し、全站規模の視覚回帰が起きる。**

したがって:

1. 各 surface の移行で、**その surface のページ側見出し規則を削除する**（canonical の `!important` は残したまま）。
2. 66 箇所すべてが消えてから、**最後に** canonical の `!important` を外し、同じ PR で Feature class の分岐（`body.page-feature`）を追加する。

Feature class を先に作りたい場合、その分岐も一時的に `!important` を必要とする（canonical がまだ `!important` を持っているため）。**それは軍拡競争の再生産なので採らない。** Feature class の実装は最終段に置く。

## §4.10 判断手順 `[確定]`

新しいテキストを置くとき、この順で決める。

1. **これは見出しか？** → §4.3 で級を決める（文書構造で決める。見た目で決めない）。

# §20 版管理と適合

## §20.1 版番号の意味 `[確定]`

> **討論 7（2026-09-14）で合意。** 既存標準（AIOIS-10 / HAID）と同じ「追加は小版、既存の行は動かさない」規律に従う。

本規範は `Design v<MAJOR>.<MINOR>` で版を付ける。既存標準（AIOIS-10 / HAID）と同じ規律に従う —— **追加は小版。既存の行は動かさない。**

| 種別 | 条件 | 例 |
|---|---|---|
| **MAJOR** | 既存ページが**違反になる**変更 | 段の削除・改名、値の変更、規則の厳格化、page class の廃止 |
| **MINOR** | 既存ページが**違反にならない**追加・明確化 | 段の追加、役割行の追加、根拠の補足、新しい page class |
| **PATCH** | 規範的変更なし | 誤字、表現、リンク修正 |

判定規則: **「この変更を入れたとき、今まで通っていたページが CI で落ちるか？」** 落ちるなら MAJOR。落ちないなら MINOR。

- PATCH は版番号に出さない（`v1.0` のまま）。改訂履歴にのみ記す。
- 版を上げるときは §20.3 の改訂履歴に**追記する**。過去の行を書き換えない。

### 最重要 — 機械的に置換してはならない

**この表は「役割が判別できないときの既定値」である。役割が分かる場合は §4.7 の早見表を優先する。**

具体例:

- `0.95rem`（15.2px、**44 箇所**）は最近傍だと `--t-body`（16px）になる。しかしその多くは**次要文字・カードのメタ情報**として使われており、役割で引けば `--t-sm`（14px）が正しい。機械的に置換すると**副次情報が本文と同じ大きさになり、階層が消える**。
- `1.15rem`（18.4px、21 箇所）は現行 H2 の値。§4.3 で H2 は 22px に上がるため、**H2 として使われているものは `--t-h2`**、カード標題として使われているものは `--t-h3`。
- 12px 未満（`0.66rem`〜`0.74rem` など **約 95 箇所**）は一律 12px に切り上げる。下限規則（§4.2）に例外はない。

**判断手順:** ①その要素の役割を §4.7 で引く → ②表に無ければ最も近い役割に寄せる → ③それでも決まらない場合のみ上の対応表を使う。

## §21.4 alias 層（第 2 層）の扱い `[確定]`

`--fg` / `--fg2` / `--fg3` / `--accent` / `--accent-2` / `--border` などの第 2 層は、第 1 層と **RGB が一致しない**（§2.1）。

**移行時に第 2 層を第 1 層へ置換してはならない。** 置換すると色が変わる（例: `--fg2 #7A6F5E` → `--ink-2 #5a4a3a` は明確に濃くなる）。

| 状況 | 扱い |
|---|---|
| 既存コードが第 2 層を使っている | **そのまま残す。** 字号・余白のトークン化だけを行う |
| 新しく書く CSS | 第 1 層のみ |
| 第 2 層がコントラスト契約（§2.2）に違反している | **色の是正は独立した PR にする。** 字号移行と混ぜない |

色の統合（第 2 層の廃止）は v1.0 の範囲外である。着手するなら MAJOR 改訂として別途合意する（§20.1）。

## §21.5 検証手順 `[確定]`

各 surface の PR で、以下をすべて実行する。

```bash
bun run typecheck
bun run test
bun run build
bun run verify:gates
git diff --exit-code          # 生成物の差分が残っていないこと
```

### 視覚回帰

**トークン追加（step 1）以外の surface では必須。** 変更前後で同じページを撮って比較する。

```bash
# 変更前（origin/preview）と変更後で、対象 surface の代表ページを
# PC 1440x900 / SP 390x844 の両方で撮影し、目視で差分を確認する。
# 意図した差分（字号の統一など）以外が出ていないことを確認すること。
```

確認すべきページは surface ごとに [`DESIGN_CONFORMANCE.md`](DESIGN_CONFORMANCE.md) の「範囲」列にある。`detail`（556 ページ）と `hub`（約 37 ルート）は全件ではなく代表 3〜5 ページでよい。

### CI と Vercel の役割分担

| | 走るもの | 文書のみの変更のとき |
|---|---|---|
| GitHub Actions `quality` | `test` / `typecheck` / `build` / `verify:gates` / `git diff --exit-code` | **走る**（paths フィルタ無し） |
| Vercel build | 同等の `buildCommand` | **スキップされる**（`ignoreCommand`） |

`scripts/vercel-ignore-build.sh` が「文書のみの変更」を判定して Vercel の build を飛ばす。**検証は GitHub Actions 側が担保する**ため、preview / main へ到達しうる変更で検証を逃れるものは無い。

スキップの対象外（＝文書でも必ず build する）:

- `docs/HAID.md` — `src/site/haid-spec.test.ts` が逐字一致を検証している
- `docs/SCORING_RUNBOOK.md` — `scripts/check-geo-freshness.ts` が「現行 batch」節を検証している

コード変更を含む PR では従来どおり Vercel が build し、プレビュー URL が出る。
